# Collectibles data-service review

The supplied review was checked against the current implementation and PredictNext's architecture. Its main recommendation is retained: background data services own new server reads through the Messenger/query proxy. PredictNext is a Kalshi-first implementation with useful responsibility boundaries, not a completed multi-provider framework. Rows marked 2026-11-10 record the later move of owned cards and offers to the data service.

| Review item               | Decision and implementation                                                                                                                                                                                                                                                                                                                                                                                                               |
| ------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Duplicate public reads    | Remove unused provider/controller `getPacks`, `getGreatestHits` and `getPackInventory` methods/actions. The data service owns these reads and their cache; inventory projection is shared within that service. Existing UI hooks already use this path.                                                                                                                                                                                   |
| Workflow versus transport | Keep the PredictNext separation: `PackPartnerProvider` owns uncached workflow calls and `PackPartnerDataService` owns cached display reads. Both use the validated client in `services/clients/PackPartnerApiClient.ts`. Workflow-controlled polling and fresh offer checks are separate from read-cache retries; terminal outcomes invalidate affected reads.                                                                            |
| Operation recovery        | Controller metadata feeds the standard Engine persistence subscription and its 200 ms debounce. Saved references support recovery by memo, without signing or submitting again; the latest unflushed update can be lost on abrupt termination. Signed bytes are never persisted. [Recovery and persistence](../../app/components/UI/Collectibles/services/data/recovery-persistence.md) documents the shared storage path and its limits. |
| Ownership projection      | Superseded on 2026-11-10. PackPartner's cards API is authoritative: owned cards are a `PackPartnerDataService` read (`getOwnedCards`), with no local card state, merge rule, indexer grace or tombstone. Sold-card history comes from Collectibles API. `syncAccount` and `syncCards` are removed.                                                                                                                                        |
| Social mutations          | Introduce command hooks. Invalidation and refresh belong to the Social service, targeted by viewer and affected query family. A background refetch is needed because UI observers live behind the proxy.                                                                                                                                                                                                                                  |
| Public openings           | `PackPartnerDataService:getRecentOpenings` serves REST snapshots. The hook owns configurable polling, a bounded insertion queue and pause/resume. No socket service or controller feed cache.                                                                                                                                                                                                                                             |
| Local search              | Subscribe to already-cached public inventory and Greatest Hits data. Remove the Greatest Hits fetch from search, which otherwise fans out across all inventories. No global-search completeness is implied. Current-account holdings come from the owned-cards read.                                                                                                                                                                      |
| Second execution provider | Defer the generic product/capability framework until a concrete second provider requires it. PackPartner, Collectibles API and Social are complementary services.                                                                                                                                                                                                                                                                         |
| Backend client injection  | Engine injects two self-contained static clients, `MockCollectiblesApiClient` and `MockCollectiblesSocialApiClient`, behind the same DataService contracts. There is no alternate application mode or mutable backend simulation. Live contracts/auth/error/reconciliation remain prerequisites; environment/viewer isolation is preserved.                                                                                               |

The [data-service boundary](../../app/components/UI/Collectibles/services/data/README.md), [search contract](../../app/components/UI/Collectibles/views/CollectiblesSearch/README.md) and [recovery requirements](../../app/components/UI/Collectibles/services/data/recovery-persistence.md) record the resulting responsibilities.

Validation uses mocked HTTP, signing and optional backend clients. No real transaction or Social publication is performed. Recovery tests restore a serialized state projection; they do not certify native disk durability during process termination.

## Validation boundaries

Use the [module validation commands](../../app/components/UI/Collectibles/README.md#validation) for current results rather than treating an earlier test count as evidence for a later change.

- Client tests cover response validation, memo correlation, safe errors and read cancellation. DataService integration tests exercise HTTP validation, Messenger, cache invalidation and the UI query proxy.
- Controller/Provider tests cover reviewed purchase and sale intent, ambiguous submission failures, reconciliation, account/environment isolation and recovery from a saved projection.
- Controller metadata and operation-state tests cover persistence filtering, retention and reset. `persistConfig.test.ts` exercises a Collectibles round trip through the standard controller file. Collectibles uses the shared Engine persistence flow rather than a feature-specific storage suite.
- Hook/component-view tests verify targeted reads, cached screen states, navigation, live subscription cleanup and the shared static backend-client contracts. Fixtures do not expose legacy server-read methods on the Controller.
- Native process termination during physical I/O, video playback, WebView motion and gestures require separate device validation. A serialized restart test does not certify hardware durability.

The boundary contracts, business-rule test inventory and agent index should be updated together when ownership or recovery rules change. No real purchase, sale or Social publication is required by these suites.
