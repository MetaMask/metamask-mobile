1 · Current Architecture

🧟 God Controller

60+ public methods, 2,600 lines. Owns state, data fetching, trading, transactions, and analytics all in one class. The controller test alone is 9,400 lines.

🔀 Monolithic Provider

PolymarketProvider mixes API calls, transaction building, caching, data transformation, and auth in a single 2,000-line file. Impossible to test in isolation.

📋 Duplicated Hooks

37 hooks where many are thin wrappers around a single controller call. The buy flow alone requires importing 7 separate hooks that all talk about the same thing.

🧩 Component Explosion

45 component directories with 7 near-identical market card variants, 6 bet button variants, and 6 skeleton variants — each a separate directory.

📛 Wrong Domain Language

What Polymarket calls an "event" is a "market" in old code. What they call a "market" is an "outcome." This creates confusion with every new developer and every future venue.

🧪 Bloated Tests

87,000 lines of test code (2.38:1 ratio). 78% of test files duplicate the same mock setup. Tests are brittle and break on every refactor.

Current Architecture — God Controller Pattern

2 · Target Architecture

PredictNext is a four-layer system designed around deep modules with slim interfaces. Complexity is pushed downward into services. The controller becomes a stateless composition root. Venue-specific logic is completely hidden behind a single canonical contract.

3 · Design Principles

PredictNext is built on four core principles drawn from John Ousterhout's A Philosophy of Software Design.

📦
Deep Modules, Slim Interfaces
Modules hide large amounts of complexity behind small, stable public APIs. Services expose 3–5 actions maximum. The controller has only 2 methods: initialize and destroy.
⬇️
Pull Complexity Downward
Retries, circuit breakers, state machines, transaction sequencing, reconnection, and cache invalidation all live in services. Higher layers express intent, not protocol steps.
🚫
Define Errors Out of Existence
Make errors impossible for callers to experience: HTTP failures are retried internally, deposit-before-order sequencing is hidden, venue failures normalize to one error model.
🏗
Different Layer, Different Abstraction
Venue adapters speak venue protocol. Services speak product capabilities. Hooks speak React. Components speak presentation. Layers never borrow another layer's language.

4 · Service Layer

PredictNext uses six deep services in three canonical shapes, plus a stateless composition root and two injected helpers.

Service Shapes
Stateful Service
Extends BaseController. Owns a Redux slice. Observable via selectors.
PredictSessionService · TradingService
Read Service
Extends BaseDataService. Owns a TanStack query cache. No Redux slice.
MarketDataService · PortfolioService
Runtime Service
Plain class. Transient lifecycle state in private fields. No Redux, no cache.
TransactionService · LiveDataService
🏗

PredictController

Composition Root

Stateless composition root. Instantiates and wires the six services in dependency order. Transactional fail-closed bootstrap.

  • Public API: initialize() · destroy() — nothing else
  • Constructs predictAnalytics helper and injects into services
  • Constructs FundingExecutor primitive and shares it
  • Not on any read or write hot path
🔐

PredictSessionService

Stateful · BaseController

Owns venue session lifecycle. Returns session-bound PredictClient views. Manages AccountReadinessPolicy internally.

  • getClient(ownerAddress, venueId?)
  • invalidate(ownerAddress)
  • fetchAccountReadiness(ownerAddress)
  • Redux slice: readinessByOwner · eligibility
📊

MarketDataService

Read · BaseDataService

Read model for event and market discovery. TanStack Query cache with descriptor-driven stale times and retry policies.

  • getEvents · getEvent · searchEvents · getCarouselEvents
  • getPriceHistory · getPrices · getCryptoPriceHistory
  • Exposes MarketDataReadModelWriter for cache patches
  • Stale times: prices 1m · events 5m · resolved 1h
💼

PortfolioService

Read · BaseDataService

Read model for account-specific data. Manages optimistic cache patches for order lifecycle events.

  • getPositions · getBalance · getActivity · getUnrealizedPnL
  • Exposes PortfolioReadModelWriter for write/live services
  • onOrderSubmitted / onOrderConfirmed / onOrderFailed
  • Cache stale: positions 1m · activity 5m · balance 1m
📈

TradingService

Stateful · BaseController

Owns the complete active-order workflow as a discriminated union state machine. The deepest module in the system.

  • previewOrder · placeOrder · cancelOrder · reset
  • States: IDLE → PREVIEWING → DEPOSITING → PLACING → SUCCESS | ERROR
  • Calls FundingExecutor directly for order funding
  • Calls PortfolioReadModelWriter for cache coordination
💳

TransactionService

Runtime · Plain Class

Public user-intent layer for deposit, withdraw, and claim. Wraps FundingExecutor with user analytics and error normalization.

  • deposit(params) · withdraw(params) · claim(params)
  • Wraps FundingExecutor.executePlan with user-intent semantics
  • User-facing analytics, retry policy, error normalization
  • Does NOT handle order funding (TradingService does that)
📡

LiveDataService

Runtime · Plain Class

Owns WebSocket lifecycle, reconnection, multiplexing, and channel fan-out. Pushes updates to read services via writer interfaces.

  • subscribe(channel, params) · unsubscribe
  • Calls MarketDataReadModelWriter.applyPriceUpdates
  • Calls PortfolioReadModelWriter.applyPortfolioUpdate
  • Replaces GameCache + TeamsCache with write-through cache
📦

FundingExecutor + predictAnalytics

Injected Helpers

Constructor-injected primitives. Not registered as Engine.context entries. Not accessible from hooks or views.

  • FundingExecutor: executePlan · cancel · destroy
  • predictAnalytics: track(event, properties)
  • FundingExecutor shared by TransactionService + TradingService
  • analytics injected into every service that emits events

5 · Data Flow Diagrams

How data moves through the system for the three canonical flows: reading market data, placing an order, and receiving real-time updates.

📖 Reading Data — Event List (PredictHome → Events on screen)
1
PredictHome renders → useEventList(params)

Hook calls useInfiniteQuery with the descriptor key from marketDataQueries.getEvents(params). One hook = one query, no wasted calls.

2
Query routes to MarketDataService via messenger bridge

@metamask/react-data-query routes the query key to the registered service action. TanStack Query deduplicates concurrent requests automatically.

3
MarketDataService.getEvents() → fetchQuery with descriptor

Service consumes the marketDataQueries descriptor for stale time, account scoping, and cache key. Retry and circuit-breaker policies from BaseDataService apply automatically.

4
PredictSessionService.getClient(owner) → PredictClient

Session service validates or refreshes the session and returns a bound proxy of the active VenueAdapter. Services never pass session objects to each other.

5
client.fetchEvents(params) → PolymarketAdapter.fetchEvents(params, session) → Gamma API

Adapter calls the venue API, transforms Gamma DTOs into canonical PredictEvent[], and returns. The UI never sees Gamma DTOs, CLOB terminology, or Polymarket types.

6
Canonical PredictEvent[] populates the query cache → EventFeed widget re-renders

EventFeed widget calls createEventDisplayModel() and passes the result into EventCard. EventCard is a pure presentation component with no venue knowledge.

✍️ Writing Data — Place Order (user taps Buy → order confirmed)
1
OrderScreen → useTrading().placeOrder(params)

The view expresses intent. The hook handles no orchestration — it delegates immediately to the service layer.

2
messenger.call('PredictTradingService:placeOrder', params)

Hook addresses TradingService directly. PredictController is not on this path — it has no placeOrder method.

3
TradingService advances state machine via this.update()

State transitions: IDLE → PREVIEWING → DEPOSITING (if needed) → PLACING_ORDER → SUCCESS. Each transition is an immutable state update on the Redux slice — subscribers re-render reactively.

4
Funding check → FundingExecutor.executePlan() (if balance insufficient)

TradingService calls FundingExecutor directly for order funding. This does NOT fire user-deposit analytics or apply user-deposit retry policy — those are user-intent semantics.

5
client.submitOrder(preview) → PolymarketAdapter → CLOB API

Adapter handles CLOB order signing, L2 headers, serialization, and submission using session material from PredictSessionService. Returns canonical OrderReceipt.

6
portfolioWriter.onOrderConfirmed(id, receipt) → cache update → UI re-renders

TradingService calls the narrow PortfolioReadModelWriter directly. PortfolioService patches the positions cache. The view updates automatically from the query cache — no additional state synchronization needed.

📡 Real-Time Data — Live Prices and Game Updates
1
useLiveData → messenger.call('PredictLiveDataService:subscribe')

Hook subscribes to a typed channel (marketPrices, gameUpdates, orderbook, cryptoPrices). The channel type is a discriminated union — impossible to request an invalid channel.

2
LiveDataService → client.createSubscription(request, session) → venue WebSocket

Service manages connection lifecycle, reconnection, and channel multiplexing internally. Multiple consumers subscribe to the same channel without creating duplicate connections.

3
Venue pushes update → PolymarketAdapter normalizes → canonical payload

Adapter translates Polymarket WebSocket message format into canonical PriceUpdate or GameUpdate types. LiveDataService receives canonical types, never venue-specific socket frames.

4
marketDataWriter.applyPriceUpdates(updates) → query cache patched

LiveDataService calls named methods on the injected MarketDataReadModelWriter. Cache is patched in-place when the update has stable identifiers. Invalidation/refetch when merge safety is uncertain.

5
Query cache update → all subscribed components re-render

TanStack Query propagates the cache update to every component using that query key. UI never combines stale query results with separate overlay state — GameCache and TeamsCache are fully eliminated.

6 · Migration Plan

Inside-out migration: replace internals while keeping the external interface unchanged, then replace the interface once internals are proven in production. Zero UI disruption during Phases 1–5.

🎯 Core Strategy — Inside-Out, Bottom-Up

The migration follows a strict dependency order: venue adapter contract first → adapter implementation and session service → read services → write services → controller composition root → UI vertical slices → cleanup. Old code delegates to new code at each step. New code never imports old code. The translation layer in PredictNext/compat/ is the only bridge between old types and canonical types, and it is deleted in Phase 7.

🛡
Risk Mitigation Strategy
Zero UI disruption (Phases 1–5)
No view, hook, or component in old code is touched during the data migration. Old hooks subscribe to the same messenger events and receive the same state shapes.
Incremental delegation
Each controller or provider method delegates to new services one at a time. If one method causes a regression, only that method reverts. Partial delegation is always a stable intermediate state.
One-way dependency
Old Predict/ code may import PredictNext/ (delegation). PredictNext/ must never import old Predict/ except through the temporary compat/ bridge — which is deleted in Phase 7.
Rollback at any phase
Phases 1–5: stop delegating and revert PredictNext PRs. Phase 6: revert route switch for the affected screen. Phase 7: don't start until all screens are stable.

7 · Domain Naming Guide

One of the most impactful changes in PredictNext is correcting the domain model to match industry terminology. The compat layer handles this automatically during migration.

Old Term (Predict/) Canonical Term (PredictNext/) Why the change
PredictMarket PredictEvent What Polymarket and Kalshi both call an "event" — a top-level grouping of related markets
PredictOutcome PredictMarket The binary question within an event. Both venues call this a "market"
PredictOutcomeToken PredictOutcome The tradeable yes/no side. This is what both venues call an "outcome"
PredictOutcomeGroup PredictMarketGroup A grouping of related markets within an event
OrderResult OrderReceipt More precise — describes the confirmed result of a submitted order
getMarkets fetchEvents Verb updated to venue capability style; noun corrected to canonical
getMarketDetails fetchEvent Corrects legacy marketId-means-eventId confusion
getCryptoTargetPrice fetchCryptoReferencePrice Reference Price is the accurate term for the external crypto price anchor
providerId venueId The feature is for prediction market venues, not generic providers
