Architecture & delivery recommendation

PredictNext × Kalshi

How to ship Kalshi quickly without putting a second venue into the Polymarket-shaped legacy stack—or waiting for the entire seven-phase Predict rewrite.

Recommended

Use a Kalshi-first vertical strangler, not a whole-codebase rewrite

Build Kalshi as the first production implementation of a small, venue-neutral PredictNext kernel, through a production MetaMask backend. Keep Polymarket on the current stack while Kalshi ships. Then port Polymarket behind the proven seams capability by capability.

Do now

Account setup/readiness, remote venue calls, durable funding, balance, then FOK trading and portfolio—all behind a Kalshi flag or separate route.

Do not do

Do not finish all seven rewrite phases first. Do not add Kalshi branches to the legacy controller/provider. Do not harden the POC in place.

Port later

Move Polymarket reads, portfolio, trading, funding/claim, and live data one seam at a time after Kalshi validates the model.

Direct answer to the proposed approach: “Kalshi first, Polymarket adapter later” is directionally right. “Rewrite a whole new Kalshi codebase” is not. Build only the shared architectural kernel and the end-to-end Kalshi slices required for launch. Quality comes from putting security, identity, money recovery, and tests at the correct seams—not from implementing every speculative module before users see value.

What the PredictNext work gets right

  • Correct domain language: Event → Market → Outcome, plus explicit Venue Account, Account Readiness, Funding Plan, Claim, and Settlement concepts.
  • Correct architectural direction: venue protocol translation below product workflows; services own orchestration; UI does not know transport or custody details.
  • Useful real seams: a venue adapter/client seam, an account setup/readiness owner, and a funding executor capable of wallet transfers or venue operations.
  • Safe migration instinct: shippable increments, explicit compatibility, and vertical UI cutovers rather than a single big-bang replacement.
  • Remote-adapter insight: volatile venue logic can move behind a versioned MetaMask backend contract.

What changed once Kalshi became concrete

  • The Kalshi spec requires an ISV admin PEM and per-user PEMs returned once. A backend is therefore mandatory for production Kalshi, not merely an optional adapter deployment mode.S7
  • The POC demonstrates the core flows but also disproves several frozen assumptions: setup bypasses the documented adapter seam, signer creation is optional, one wallet address is treated as identity, and money operations need durable recovery.
  • Kalshi’s current V2 order endpoint and fixed-point schemas have already moved relative to the PDF/committed POC, which is exactly why the volatile protocol belongs server-side.S9
Read on the rewrite: the architecture is directionally strong, but the implementation plan is too horizontal and too settled before the second venue has shaped the interface. Kalshi should revise the plan, not wait behind it.

Correct the PredictNext contracts before implementation

The POC is valuable because it turns hypothetical seams into concrete failures. These changes are small compared with the full rewrite, but they are architectural launch blockers.

Current assumption Observed problem Recommended correction
Session/readiness keyed by ownerAddress Kalshi is one real-person identity with one MetaMask ISV subaccount; a wallet is not the person. Key Kalshi identity/readiness by authenticated MetaMask subject + venue. Treat the selected wallet as funding/signing context. Never accept client-supplied address/email as authorization.
Account setup is “owned” by PredictSessionService, but no adapter setup methods exist The POC calls BackendClient directly from the session service, leaking Kalshi routes above the venue seam. Add a narrow account-setup capability interface (start, submit step, resume), or make it an explicit session adapter port. Keep venue endpoints below it.
All venue reads require a session-bound client Event/market discovery is public; the POC ignores its session argument. Separate public market-data reads from account-scoped operations. Browsing should not require a selected wallet or KYC session.
One active venue; market query keys omit venueId Coexisting venues can collide on IDs/cache families and cannot support a merged feed safely. Venue-qualify IDs, routes, cache keys, readiness, events, and operations now—even if launch uses one venue per screen.
One ~30-method non-optional VenueAdapter It forces Kalshi to implement Polymarket-specific series, crypto-reference, carousel, claim, and stream methods. The branch itself says the second venue is the point to reconsider the wide interface. Freeze only the capability groups used by real slices: market data, account setup, portfolio, trading, funding. Do not use booleans plus methods that only throw when a capability can be represented structurally.
TradingService.cancelOrder exists, but VenueAdapter has no cancel method Kalshi supports resting, partial, cancel, amend, and decrease flows; the canonical receipt only models a subset. Choose launch semantics. If FOK-only, explicitly omit open-order/cancel UI. If resting orders are required, model open orders, fills, cancel, and reconciliation before launch.
Funding plan creation is side-effect free in docs The POC executes withdrawal during createWithdrawPlan. Deposit state is volatile and cannot recover after app/backend restart. Use prepare → user confirmation → commit, with operation ID, expiry, idempotency key, durable backend state, and resumable status. Persist only safe operation references on mobile.
Services absorb retries broadly Blind retries of onboarding, order, indication, or withdrawal POSTs can duplicate money/user operations. Retry reads freely; retry writes only with idempotency and reconciliation semantics defined per operation.
Separate OTP_INVALID and OTP_EXPIRED Kalshi returns one indistinguishable invalid_or_expired_code response. Expose an honest combined product error/action (“invalid or expired; resend”) instead of inventing certainty.
Funding workflow may remain transient Withdrawal has no status endpoint at launch; deposit indication can fail after an on-chain transfer. Backend operation ledger and support/reconciliation path are mandatory. Cross-screen/app-restart recovery is a money-safety requirement, not optional UI polish.

Spec mismatches that must not survive the POC

  • The POC treats both 409 variants as “link an existing user,” but the PDF says only flat {"error":"account_exists"} means link; nested duplicate external_user_id means the caller ID is wrong.
  • The POC’s setup status is only local in-memory state, while production needs durable workflow state plus authoritative recovery.
  • /link/verify lost-response 409 handling and one-time API-key response loss need explicit recovery paths.
  • Portfolio activity currently maps orders, not fills and settlements; the run guide’s settlement claim is not implemented. Kalshi exposes fills and settlements endpoints.S10
  • Preview data sent back from mobile is trusted at submit time and slippage is ignored. Production needs a server-bound quote/operation ID, expiry, max price/spend validation, and an idempotent client order ID.

Branch handling: do not merge or cherry-pick the POC wholesale. Port small verified pieces into clean production modules with tests.

Recommended delivery plan

Deliver vertical behavior, not horizontal architecture layers. Each stage is independently demoable, flaggable, and reversible.

Stage Outcome Minimum scope Exit gate
0. Correct the contract and secure the POC Team agrees on the real launch seam. Rotate keys; decide identity, separate vs merged UX, Base rail, order type, PII path, backend owner/SLO; amend docs. No unresolved P0 identity/security/product topology question.
1. Production walking skeleton An authenticated mobile request reaches Kalshi through the owned backend. Existing apiClient; runtime schema validation; backend auth; static egress; credential vault; durable operation store; venue kill switch; one read endpoint. No caller-supplied authorization identity; no secrets/PII in logs.
2. First vertical slice Setup → readiness → deposit → balance works end to end. Path A and B; resumable setup; Base USDC prepare/confirm/send/indication; operation recovery; balance refresh. Restart/network-loss/idempotency tests pass; demo payments gate works.
3. Trading slice Browse → preview → buy/sell → position/activity. Public events; FOK-only unless product requires resting; quote expiry; idempotent order submit; fills; settlements; explicit deposit first. Contract, integration, component-view, and demo E2E tests pass.
4. Withdraw + launch hardening Safe withdrawal and controlled rollout. Prepare/confirm/commit; payout-method reuse; honest “submitted” state; support reconciliation; Sentry/metrics; cohort flag; read-only/unavailable degradation. Security/privacy/compliance/ops sign-off and rollback drill.
5. Polymarket strangling The shared kernel becomes the real Predict architecture. Port public reads first, then portfolio, trading, funding/claim, live data. Legacy provider delegates until each capability reaches parity. Delete legacy capability only after production parity and replacement tests.

Why the first slice is setup → deposit → balance

Market browsing is easy and does not validate the risky differences. The first slice should exercise person-level identity, KYC/linking, server-held credentials, a one-time funding plan, an on-chain wallet action, a venue follow-up, and portfolio reconciliation. If those seams hold, the architecture is earning its keep.

Polymarket migration after Kalshi

  1. Read parity: canonical events/details/prices, optionally shadow-compared.
  2. Portfolio parity: balances, positions, activity; retain legacy claims until modeled.
  3. Trading parity: preview and submission behind the shared workflow.
  4. Funding/claim parity: move wallet-specific plans and execution.
  5. Live parity and cleanup: subscriptions, old controller/provider deletion, then decide whether the UI rewrite still pays for itself.
Compatibility code should arrive when needed. Do not build the full bidirectional legacy mapper, every Polymarket field, or editable-template funding mode as a Kalshi launch prerequisite. Add compatibility at the first Polymarket delegation slice.

Quality bar: what is mandatory and what is safe to defer

Must have before launch

  • Authenticated MetaMask subject; authorization derived server-side
  • KMS/envelope-encrypted admin and per-user keys; rotation/revocation
  • PII/SSN data minimization, no persistence on mobile, redacted logs/analytics
  • Durable setup and financial operation ledger
  • Idempotency and reconciliation for every write
  • Explicit user confirmation before transfer/withdraw/order commit
  • Versioned backend contract + runtime validation + shared fixtures
  • Service integration tests and component-view tests for each slice
  • Failure tests: app kill, timeout, duplicate submit, lost response, key loss/revocation
  • Feature flag, per-venue kill switch, observability, support runbook

Safe launch cuts

  • Base-only funding, if product/compliance approve
  • Separate/flagged Kalshi surface instead of merged multi-venue feed
  • Polling instead of LiveDataService
  • Explicit deposit before trade; no automatic deposit chaining
  • FOK-only trading; no resting-order UI, if product agrees
  • No generic remote signing-intent framework yet
  • No local Kalshi fallback; degrade to read-only/unavailable
  • No Polymarket migration before Kalshi launch
  • No full component-library rewrite
Do not use “85–90% less test code” as a migration objective. Delete old tests only when a replacement test at a deeper interface proves the same behavior. For identity, KYC, credentials, orders, and money movement, confidence—not file count—is the quality metric.

Minimum test surfaces

  • Backend Kalshi adapter: signing preimage, flat/nested errors, duplicate identities, setup resume, key mint/list/revoke recovery, rate limits, order/fill/settlement transforms.
  • Mobile ↔ backend contract: shared JSON/OpenAPI fixtures, runtime validation, error mapping, old-client compatibility.
  • Deep modules: setup/readiness transitions, funding prepare/commit/retry, order quote expiry/idempotency, portfolio reconciliation.
  • Component views: Path A/B, KYC pending/rejected, deposit interrupted/resumed, insufficient funds, order rejection, withdrawal submitted.
  • Demo E2E: one real end-to-end smoke per supported launch flow; never log the credentials or identity payload.

Time-to-market implications

The full rewrite is not a credible Kalshi critical path: its own plan requires seven phases and roughly 24–32 PRs before cleanup. The vertical plan lets backend and mobile proceed in parallel and produces a useful slice before market/trading polish.

Planning band Work Parallelism / caveat
3–5 working days Stage 0 decisions, key rotation, contract correction, production API skeleton agreement Mobile, backend, product, security/compliance together
1–2 weeks Authenticated backend walking skeleton, secret storage, durable store, remote mobile transport, first read Backend and mobile in parallel
2–3 weeks Setup → readiness → Base deposit → balance vertical slice Blocked by Kalshi demo payments gate and identity/KYC decisions
2–3 weeks Markets, FOK trading, positions, fills, settlement activity, withdrawal Can overlap UI and backend once contracts stabilize
1–2 weeks Security/privacy/ops hardening, E2E, staged rollout Do not compress money-flow failure testing

Illustrative planning hypothesis: roughly 6–10 calendar weeks with staffed mobile and backend streams, after external dependencies are available. This is not a commitment; team size, product scope, KYC/compliance decisions, and Kalshi enablement can dominate it.

Likely long poles outside mobile code

  • Production admin credentials, reserved ISV subaccount allocation, and source-IP allowlisting
  • Demo/production crypto-rail enablement
  • MetaMask authenticated-subject and multi-wallet policy
  • KYC/SSN privacy, legal, retention, and support requirements
  • Withdrawal reconciliation while no ISV-safe transfer-status endpoint exists
  • Backend ownership, SLO, on-call, and incident degradation behavior

Decisions required before production code

Priority Decision Recommended default
P0 Does Kalshi launch separately or in a merged Polymarket feed/portfolio? Separate/flagged surface for speed. If merged is mandatory, add a venue aggregator and venue-qualified query keys now.
P0 What stable MetaMask subject maps to one Kalshi person/subaccount? Derive from authenticated backend identity; use a server-generated stable external ID. Do not use wallet address or email as authorization/identity.
P0 How will SSN and other KYC data be collected and retained? Prefer a Kalshi-hosted/tokenized flow if available. Otherwise stream through the owned backend with strict minimization; never persist on mobile or log.
P0 Can launch be Base USDC only? Yes, if approved. It reuses MetaMask’s EVM transaction stack. Use address/token/network returned by the backend/Kalshi, not POC constants.
P0 Are only immediate FOK orders required? FOK-only for v1. If GTC/resting orders are required, add open-order lifecycle, cancel/amend/decrease, and fill updates before launch.
P0 Who owns the backend and its operational SLO? A named production team with on-call, static egress, credential operations, reconciliation, and per-venue kill switches.
P1 What happens during backend/Kalshi degradation? Cache/public read-only where safe; disable writes. Never fall back to putting Kalshi credentials on-device.
P1 When does Polymarket move? After Kalshi stabilizes; start with read shadowing/parity, then move one capability at a time.

Changes incorporated into the PredictNext documentation

  1. Replace the single migration critical path with two tracks: Kalshi vertical delivery now; legacy Polymarket strangling later.
  2. Make backend mediation mandatory for Kalshi, while deferring the generic remote signing-intent framework until Polymarket or another remote venue needs it.
  3. Separate person identity, Venue Account, and funding wallet in CONTEXT.md. Change readiness/session keys from wallet-only to subject + venue.
  4. Add the missing account-setup seam and stop PredictSessionService from calling venue/backend routes directly.
  5. Venue-qualify cache/query/route/operation identifiers, even if the first UI is one venue per screen.
  6. Revisit the wide adapter now, because the branch’s stated trigger—the second venue—has arrived. Keep only real capability groups.
  7. Document write safety: prepare/confirm/commit, idempotency, no blind POST retries, durable operation references, and restart/lost-response recovery.
  8. Decide order semantics explicitly: FOK-only launch or full resting-order lifecycle. Align cancelOrder and adapter methods.
  9. Correct Kalshi examples: supported deposit networks are Base, Solana, and Tempo; Base is the recommended first rail, not a hardwired Solana flow.
  10. Remove the test-reduction percentage as a success criterion. Define behavior and risk coverage instead.
  11. Defer the full UI primitive rewrite; extract/reuse venue-neutral presentation only when a Kalshi slice needs it.
