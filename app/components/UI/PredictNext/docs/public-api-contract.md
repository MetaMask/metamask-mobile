# Permanent PredictNext public API contract

PRED-1374 defines the external contract for PRED-1340. It does not implement that epic. [ADR-0002](./adr/0002-permanent-public-api-private-legacy.md) records the agreed ownership and legacy presentation exception. [PRED-1341](https://consensyssoftware.atlassian.net/browse/PRED-1341) holds the app-wide inventory and delivery tickets.

Production Polymarket must look and behave as it does today when Kalshi launches. Its presentation, internal hooks, controller, and execution stay on legacy Predict. Code outside Predict moves to permanent PredictNext APIs. There is no requirement to make legacy internals canonical.

This document specifies additions to the current contract. It does not claim that proposed exports, routes, or fields already exist. Current `types/`, `contracts/v1/`, services, and tests remain executable truth until their owning implementation changes them together. PredictNext is unreleased, so that work may make coordinated breaking changes. Do not add another API version or negotiation framework solely to support unreleased PredictNext builds.

### Read state and pagination

A supported read returns `data?`, a bounded canonical `error?`, `isLoading`, `isRefreshing`, `isStale`, and `refresh()`. A paginated read also returns `loadMore()`, `hasMore`, and `isLoadingMore`. An unsupported read is explicitly `status: 'unsupported'`, without a request, fake data, or no-op action. Hook ordering remains stable on Active Venue changes. Cached data can coexist with refresh errors. Deliver it only when its Venue and account scope match the consumer's resolved context; correctly scoped inactive-Venue caches may remain private. Empty is a completed read with no entries, not loading, unavailable, or unsupported.

Feed selections are product choices already used by Home and Explore, such as trending, sports, or a configured BTC interval. The private implementation maps those choices to supported feeds/queries. Do not invent a universal category expansion project. `limit`, filters, ordering selection, and normalized search text belong in exact cache keys.

The implementation owns response order and opaque cursors. External callers do not sort each page, synthesize offsets, or reconstruct a cursor. Refresh starts a new pagination chain. Bind a cursor to Venue, account scope when relevant, selection, and ordering; reject use in a different context. Suppress duplicate load-more calls. Stable tie-breaks prevent duplicate/missing Activity rows at page boundaries. The implementing pagination contract must make absence of `nextCursor` mean the selected history is exhausted, not that a fetch cap was hit. Today's Kalshi Activity merge can stop at five upstream pages and report early completion. PRED-1380 owns upstream-cursor-aware traversal, an honest bounded/unavailable result when necessary, and stale-cursor handling that does not report an arbitrary window boundary as exhausted history. This is required implementation work, not a claim about the demo backend.

Polymarket search currently paginates; Kalshi search is ranked and unpaginated. The public search result can have `hasMore: false` for Kalshi without inventing pagination. Preserve source ranking and supported search behavior rather than forcing Polymarket into Kalshi's every-term matching rule.

The existing live-data owner under PRED-1240 remains responsible for visible subscriptions, patches, and recovery. No second live manager or hidden/inactive subscription is introduced by these APIs.

## References, identity, and navigation

Public entity references are opaque, Venue-qualified values, for example `{ venueId, eventId }`, `{ venueId, marketId, outcomeId? }`, and `{ venueId, positionId }`. External callers retain and pass them; they do not inspect them to choose a Venue. Activity additionally has its own `id`; a transaction hash is not a row identifier. Polymarket temporarily preserves the deterministic legacy `getPolymarketActivityId` composite as an opaque row ID, including its existing fields, so identical source replays retain identity. The future backend must reproduce that rule for the same source rows. That rule does not guarantee identity across upstream corrections and can collide for indistinguishable rows. PRED-1380 must verify collisions/replay behavior and identify an authoritative per-execution discriminator before claiming stronger identity or enabling cross-source dedup. Do not add a page index or random ID to hide collisions. Operation notification identity is separate from Activity row identity.

For temporary Polymarket adaptation, use Gamma Event ID for `eventId`, condition ID for `marketId`, and CLOB token ID for `outcomeId` when available. Polymarket `positionId` is the CLOB token ID, matching legacy `PredictPosition.id` and v2 `token_id`, within its privately resolved account scope. Kalshi `positionId` is a deterministic encoding of Market identity plus held side within its Venue Account scope; do not conflate opposite-side holdings. A Position action validates the current account scope before rehydrating or trading. Gamma Market ID stays a distinct private catalog identifier. PRED-1356 must preserve these public identities or resolve them behind the same API. Never relabel an outcome index as a token ID. If only the condition is known, a historical entry can retain `marketId` without a binary side or Outcome reference. Missing identity enrichment does not make an existing financial row disappear.

Canonical Event Markets still require exactly one Yes and one No Outcome. Parallel arrays can establish a token-to-label association if the upstream contract guarantees alignment, but array position or custom label cannot establish canonical Yes/No. The inspected legacy code does not supply an authoritative structured side mapping for all custom outcomes. PRED-1375 must identify and test that source before publishing those Markets canonically. A backend catalog is useful only if its own mapping has authoritative provenance. Do not move an index-based guess into the backend and call it authoritative. Private legacy presentation can continue using its existing interpretation without exposing an invented canonical side. This is a named prerequisite, not permission to omit an existing Polymarket section at launch.

`openPredict(intent)` accepts a product intent, such as home, portfolio, a Venue-qualified entity reference, or a supported account action, plus supported attribution. It validates the reference against the resolved context. Pre-submit account actions revalidate readiness and eligibility. No external caller passes legacy route names, provider IDs, token arrays, proxy-wallet data, or raw legacy objects.

V1 visible data is Active-Venue-only. A known foreign-Venue reference yields bounded unsupported/not-found. It does not change preference, reinterpret the identifier, or silently fall back. Unmarked historical links retain their known Polymarket origin. PRED-1294 owns later cross-Venue content resolution; this limitation does not satisfy that larger epic.

### Rolling Series

Keep immutable Event identity separate from following a Series. `usePredictCurrentEvent(seriesReference)` returns the selected Event and replaces it atomically on a window change. An explicit follow-Series intent can keep following; a fixed Event link, Position, or historical Activity never rotates. Cancel an unsubmitted preview when the selected Event changes. Retain the ended Event under its original cache key while the next Event is unavailable.

Kalshi's backend selects the current Event through `GET /v1/venues/{venueId}/series/{seriesId}/events/current` once implemented. The temporary Polymarket implementation preserves `useCurrentPredictMarketFromSeries` / `utils/series.ts` selection, timing, foreground recovery, and prefetch behavior privately. External callers do not calculate windows or choose from Series arrays. Do not rewrite legacy rolling screens to match a new hook.

## Minimal canonical financial additions

All quantities and money use validated decimal strings. Percentages use signed decimal strings in percentage points, so `12.5` means 12.5%, not 0.125. Financial arithmetic uses decimal/fixed-point operations. Never round shares to whole units at the public boundary.

### Probability and quotes

Add optional `Outcome.probability: { value, basis, observedAt }`, where `basis` is `midpoint | last_trade | venue_mark`. This is a display projection, distinct from `askPrice` and `bidPrice`. Copy the actual source meaning; do not relabel a mark as a last trade. An absent quote stays absent. A missing/empty source must not become `0`, and probability never becomes an Ask fallback in canonical data. A genuine zero remains distinct from absence when supported by the source.

Polymarket Gamma `outcomePrices` and legacy `token.price` supply displayed probability, not proof of an executable Ask. Price/book endpoints and structured CLOB quotes supply true Bid/Ask values. Existing legacy buy-button fallback remains an internal presentation behavior, not a canonical quote guarantee. An Order Preview, not a displayed odds value, authorizes execution. Do not silently change legacy UI while improving the canonical mapping.

### Positions and summary

Add stable `positionId`, optional canonical `outcomeId`, and independently optional `valuation` fields:

```ts
valuation?: {
  observedAt: PredictTimestamp;
  currentValue?: PredictAmount;
  costBasis?: PredictAmount;
  unrealizedPnl?: PredictSignedAmount;
  unrealizedPnlPercent?: PredictSignedAmount;
  averageEntryPrice?: PredictDecimal;
};
settlement?: { mode: 'claim' | 'automatic'; claimableAmount?: PredictAmount };
```

For account rows only, allow absent `side` when authoritative side metadata is unavailable. Keep shares, condition identity, available source financial values, and historical display metadata. That does not weaken the two-Outcome Event invariant. An incomplete reference cannot authorize an Order; resolve and validate the held Outcome privately first. `marketExposure`, `currentValue`, realized PnL, and unrealized PnL remain distinct. Keep existing optional `realizedPnl`, `feesPaid`, and `totalTraded` semantics.

The summary projection is `{ venueId, observedAt, availableBalance?, openPositionsValue?, claimableValue?, portfolioValue?, unrealizedPnl?, unrealizedPnlPercent? }`. Every supplied summary field covers its complete applicable population, never only fetched pages. An empty, authoritatively complete portfolio can report zero. An incomplete/unavailable population cannot. The summary failure does not erase a successful Balance or Position read. The existing Polymarket provider silently caps position traversal at five pages per cohort and does not return completeness. An unchanged legacy hook therefore cannot prove a complete summary for large portfolios. PRED-1378 must privately enumerate the authoritative full source or expose a reliable completeness signal through a private reader, without rewriting legacy screens/hooks. Until proven complete, omit affected totals and report unavailable; never relabel a capped legacy result as a complete canonical total. Balance can still succeed independently.

For Polymarket, preserve source `currentValue`, `initialValue`, `cashPnl`, `percentPnl`, `avgPrice`, realized PnL, claimability, and existing display thresholds. A complete legacy summary uses the same membership as `usePredictPortfolio`: open Positions; actionable claimable Positions; available Balance. `portfolioValue = availableBalance + openPositionsValue + claimableValue`; open unrealized PnL is the complete open current value minus complete open entry cost. Percent is omitted when cost is zero. Do not reinterpret source fee treatment, double-count claimable holdings, or sum displayed/rounded rows. Optimistic updates remain provisional presentation and reconcile with authoritative reads; they are not a new authoritative valuation source.

PRED-1378 must approve Kalshi's valuation methodology with API/product owners before implementation: price basis, absent bid/liquidity, fee inclusion, cost-basis membership, rounding, and stale/partially unavailable values. This document does not select an unverified liquidation estimate. Its current backend has none of these valuation/summary projections. Do not use `marketExposure` or mobile float math as a fallback. An old observation remains visibly stale, not current merely because a request completed.

### Fractional Cash Out

The permanent sell intent is `{ action: 'sell', marketId, side, shares }`, with a positive decimal share quantity. Its owning public action captures Venue/account context; external callers do not pass a Venue selector. Prepared quantities and execution results must also support decimal strings, not integer JavaScript numbers. Keep the single action-discriminated buy/sell workflow. Quantity precision/minimum/step constraints belong to the selected implementation, not a caller's Venue branch. Kalshi's current Preview wire accepts integer `contracts` only and must still reject fractional sales. A fractional Kalshi holding remains visible even when its remainder cannot be sold. Polymarket retains its existing fractional Cash Out. No rounding, hidden remainder, or protocol rewrite is authorized.

This qualifies ADR-0001's whole-contract assumption as Kalshi-specific; it does not change the currently implemented parser. PRED-1379/1383 own public action adaptation and lifecycle; PRED-1378 owns Position/quantity projections. Any new remote fractional wire support belongs to that Venue's implementing backend change, not a relaxation of Kalshi validation.

## Activity and historical metadata

Keep `fill | settlement` as the domain variants. A Claim is the explicit operation that can produce a Settlement, not a fabricated trade. Add these fields to account Activity where evidence exists:

- `transactionReferences?: { chainId, hash }[]`. Both fields come from real transaction evidence. An off-chain Kalshi row has no fabricated Polygon chain or explorer hash. Row IDs remain separate even when multiple rows share one transaction.
- `display?: { title?, outcomeLabel?, imageUrl? }` for source-provided historical presentation independent of a live catalog join. Validate approved images. Optional `context` continues to carry navigable canonical Event/Market/Outcome context when available. Do not infer navigation or Yes/No identity from display text.
- Fill `execution?: { action: 'buy' | 'sell'; side: 'yes' | 'no' }` only when both transacted action and side are authoritative. Fill `shares?` is absent when the source does not report size, as allowed by the existing Polymarket Activity DTO. `amount?` retains the reported settlement-currency execution amount; an absent size never becomes amount divided by price. Optional `pnl: { netPnl?, totalNetPnl?, observedAt? }` preserves the distinct source `netPnlUsd` and `totalNetPnlUsd` values used by legacy Activity details. Do not collapse market and total net PnL, or substitute proceeds for PnL in canonical data. Private legacy detail presentation keeps its existing fallback behavior.
- Fill `outcomeSide?` and `price?` are an inseparable reported-side pair. They can be absent for metadata-poor records. `execution` can be absent even when that pair is known. Polymarket BUY/SELL evidence enables corresponding copy only after the Outcome is authoritatively resolved. When identity is incomplete, historical source labels may still be displayed without claiming a canonical side.
- Settlement `mode: 'claim' | 'automatic'`, `result?`, existing held `side?`, `shares?`, `proceeds`, optional `costBasis`, `fee`, the same optional source `pnl`, timestamp, and references. `result` remains `yes | no | scalar` when known. Absence means unavailable, never a fabricated fourth resolution or a result inferred from payout. Held side is not winning side. Mode comes from an explicit redemption or automatic-settlement source, never guessed from Market lifecycle.

Kalshi maps `outcome_side` to `outcomeSide` and selects the corresponding `yes_price_dollars` or `no_price_dollars`. Its documentation describes exposure, while demo behavior has echoed transacted side. Preserve the reported pair and use neutral Fill copy without asserting bought/sold or using that side as Position identity. Do not reconstruct action from deprecated `action`/`side` fields. Contract examples cover both interpretations. A backend discriminator is not required merely to display a neutral Fill. This contract does not claim the upstream semantic ambiguity is resolved.

Kalshi settlement `market_result` is authoritative per row even when catalog context is missing. Polymarket redemption history may have only condition identity, amount, timestamp, hash, and source display metadata. Preserve that record with `mode: 'claim'` and absent `result`; a durable authoritative join may enrich it, but is not required for keeping the row. Missing result or context is not a parser error. Activity `timestamp?` preserves an authoritative execution/settlement time when available. The inspected upstream DTO requires it, but legacy mapping defensively defaults a missing time to `Date.now()`. Canonical adaptation must never invent that time. If the actual source omits it, keep the record undated and preserve source sequence within its page; PRED-1380/1387 must support date-unavailable presentation in shared Activity instead of assigning it to today. Undated rows do not authorize chronology-based joins. Malformed supplied money, identity, timestamp, or enum still fails validation. Do not catch a bad row and silently filter it out. Preserve previously loaded valid data with an error, rather than presenting a failed page as empty/exhausted history.

Existing Polymarket filters, including zero-payout REDEEM exclusion, stay as current product behavior. This work neither removes those filters nor introduces new losses. The prohibition is on losing previously visible history to satisfy canonical fields. The legacy mapper's generic non-TRADE-to-claim conversion is not authoritative provenance; use upstream record type before it is discarded. If an upstream kind that was visible cannot be classified truthfully, PRED-1380 must resolve it before caller migration, not silently drop or relabel it.

Shared Activity needs neutral Fill and automatic Settlement kinds, optional chain/transaction references, and canonical detail navigation. PRED-1380/1387 must coordinate the owning `@metamask/client-utils` release if its types require changes. Funding transfers remain funding records; operation progress and submitted Orders are not execution Activity. Do not label an ambiguous operation successful because a transaction callback fired.

## Presentation and operations

Public wrapper props contain canonical references/data, supported attribution, privacy state, and narrow callbacks. Callback results remain canonical. Wrappers own any legacy rehydration and delegate to legacy components/hooks; legacy components may keep their old internal props and callbacks. Do not rebuild or restyle them. For example, a public `PredictPositionRow` can privately invoke legacy position presentation while an external `onPress` receives a canonical Position reference rather than the whole legacy Position object. The same applies to discovery card buy regions and Activity detail interactions.

For new Kalshi UI, normal children-based composition and explicit variants still apply. Private legacy delegation is a scoped exception to the no-copy/rebuild guidance, not permission to introduce boolean mode props or conditional hook calls in external consumers.

Supported actions are absent when unimplemented. Dynamic unavailability is a bounded state distinct from unsupported capability; readiness and backend authorization still apply at execution. A Venue descriptor cannot enable missing executable code. Browse access does not require trade readiness. External consumers receive supported deposit/withdraw/claim/Cash Out actions without reconstructing eligibility rules.

An operation reference is `{ venueId, operationId }`. The owning service privately binds it to the original person/account scope and rejects references it cannot resolve for that person before obtaining credentials. A reference alone is neither authorization nor permission to submit again.

Operation presentation contains that safe reference, kind, phase/status, frozen amount/currency, optional genuine transaction references, destination/network/asset display context when applicable, and only supported confirm/cancel/reobserve actions. These are mobile-only view contracts derived from the owning workflow. They do not carry raw `TransactionBatch`, proxy-wallet state, backend bearer tokens, step-up proofs, or an arbitrary protocol payload. Exact signing/submission material stays in the funding or private legacy execution owner and existing confirmation pipeline.

A withdrawal source balance is a synchronous projection bound to the original operation's account scope, not today's Active Venue. A submitted operation keeps its original Venue, account, Funding Wallet execution context, amount and destination. Switching Venue or wallet for the same person cannot redirect it or suppress completion. Deduplicate notifications by scoped operation identity and terminal transition, retaining existing suppression rules. True identity replacement stops old-person observation/display; never obtain the new person's token for an old operation. PRED-1383/1390 own these lifecycle and notification changes.

Cancel unsubmitted intents/previews on relevant context changes. After Commit, observe rather than resubmit. Order observation remains in memory through screen closure and same-person switches, only for the current process. No mobile Order persistence or process-death notification guarantee is introduced. The API already stores profile-scoped operations and can observe an existing operation via repeated `{ previewId }` Commit, even after Preview expiry. That capability alone is not a mobile restart-recovery feature. Authoritative portfolio/Activity reads reveal completed effects after restart.

Kalshi Base USDC plans, one-time amount-specific deposit addresses, frozen withdrawal destinations, step-up, signing, and backend reconciliation remain PRED-1161/1163 responsibilities. Editing a bound amount invalidates/reprepares the plan. Do not reuse legacy proxy-address math or Polygon constants for Kalshi. Do not piggyback on funding durability to promise Order durability.

## Cache and context lifetime

PRED-1381 changes account query identity and result acceptance, not public caller parameters. The runtime owner derives opaque, non-persisted `personScopeId` and `accountScopeId`. Keys contain no profile subject, wallet address, credential, or authorization payload. The account scope resolves to the person's Venue Account for Kalshi and additionally the relevant Funding Wallet/account for wallet-scoped Polymarket.

Account query key shape is `[serviceAction, venueId, personScopeId, accountScopeId, generation, params?]`; its invalidation family omits params. This applies to Balance, Positions, Activity, summary, readiness and other account projections. Scope is `account`, not the currently declared `venue`. A same-person wallet switch changes Polymarket scope, but does not arbitrarily create a different Kalshi portfolio. Increment generations on identity/account replacement or invalidation that would otherwise admit late data into a reused scope.

Keep a separate selection generation for active reads and previews. A Venue switch cancels visible old-Venue requests and rejects their late results, while retaining correctly scoped caches and submitted-operation observers for the same person. Public market-data keys stay Venue/selection-qualified and person-independent. Account keys never derive solely from Venue or the selected wallet.

True person replacement/logout cancels account reads, clears account caches and private presentation state, rotates scope identifiers/generations, and disposes old-person observers. Check captured scope/generation before delivering any async result, including a legacy callback, so cancellation-resistant responses cannot repopulate or display old data. Submitted operations retain their original scope separately from current selection and never rebind credentials. A token refresh for the same authenticated person is not a person replacement; alias/account continuity must be resolved by the identity owner, not guessed from raw token text.

## Deletion and verification
